本篇对应原书第 32 和第 33 章。

并发错误难处理，不只是因为代码复杂，还因为错误经常和时机有关。调度顺序、负载、机器数量、日志位置稍微变化，问题就可能隐藏或暴露。

所以学习并发 bug，重点不是背几个事故名称，而是识别常见故障模式。

## 先把 bug 分成两类

并发 bug 可以先分成两类：

- 程序还在跑，但结果错了。
- 程序不再往前走。

前者常见于原子性违反、顺序违反和数据竞争。后者最典型的是死锁，也包括活锁、饥饿等推进性问题。

这样分完之后，排查思路会清楚很多。结果错误时先找共享状态和不变量；无法推进时先找等待关系和资源依赖图。

## 非死锁缺陷

很多并发 bug 并不是死锁，而是程序继续运行，但结果错了。

常见两类：

第一类是 **违反原子性**。代码本来假设一组操作不会被其他线程插入，但实际发生了交错，导致状态不一致。

第二类是 **违反顺序**。一个线程假设另一个线程已经完成初始化或状态更新，但事实并非如此。

修复这类问题时，不要只想着“加一把锁”。先问清楚：

- 哪些操作必须作为整体？
- 哪些状态必须先发生？
- 哪个线程负责发布这个状态？
- 其他线程如何可靠观察到它？

如果问题是顺序关系，单纯加锁未必能表达清楚，可能需要条件变量、信号量或更明确的状态机。

例如一个线程负责初始化对象，另一个线程负责读取对象。如果读取线程只检查指针非空，却没有可靠等待初始化完成，就可能读到半初始化状态。这不是单纯“同时写一个变量”的问题，而是发布顺序不清楚。

## 死锁

死锁发生时，多个线程互相等待，系统无法继续推进。

死锁需要四个条件同时成立：

1. 互斥：资源不能被多个线程同时持有。
2. 持有并等待：线程持有一些资源时继续等待其他资源。
3. 不可抢占：资源不能被强行拿走。
4. 循环等待：线程之间形成等待环。

破坏任意一个条件，都能避免死锁。

在真实代码里，死锁往往不是出现在单个函数里，而是跨多个模块形成。A 模块先拿配置锁再拿连接锁，B 模块先拿连接锁再拿配置锁，单看各自都合理，组合起来就可能形成环。

## 锁排序

实践中最常用的死锁预防方法是锁排序。

如果所有线程都按照同样顺序获取锁，就不会形成循环等待。

例如规定总是先拿 A 再拿 B，那么下面这种情况就不会出现：

- 线程 1 拿着 A 等 B。
- 线程 2 拿着 B 等 A。

如果锁集合无法静态确定，可以用锁地址或唯一 ID 建立全局顺序。

## try-lock 和重试

另一种思路是拿不到锁就释放已有锁，稍后重试。

这可以避免持有并等待，但会引入新问题：

- 代码复杂度增加。
- 可能出现活锁。
- 重试策略需要小心设计。

所以 try-lock 不是万能解药。它适合某些低层系统代码，但在普通业务代码里经常会让控制流更难读。

## 事件驱动并发

线程不是唯一并发模型。事件驱动模型用一个事件循环处理多个连接或请求，典型接口是 `select()`、`poll()` 或更现代的事件通知机制。

它的好处是很多逻辑在单线程内执行，共享状态少，因此不需要大量锁。

但它也有自己的复杂度：

- 任何阻塞调用都会卡住整个事件循环。
- 长任务需要拆成状态机。
- 异步 I/O 和错误处理会让控制流变散。

事件驱动不是消灭复杂性，而是把“线程交错和锁”的复杂性，换成“状态管理和非阻塞接口”的复杂性。

所以事件驱动服务器有一条硬规则：事件循环里不能做长时间阻塞操作。

如果一次磁盘读取、数据库查询或外部接口调用会阻塞，就要使用异步接口、线程池或任务队列把它移出去。否则一个请求慢，会拖住整个事件循环。

## 排查并发问题的基本原则

1. 先找共享状态。
2. 再找所有写路径。
3. 检查哪些读写需要原子性。
4. 检查哪些事件存在先后依赖。
5. 检查锁获取顺序是否稳定。
6. 不要用“测试没复现”证明并发代码正确。

并发正确性最好靠结构，而不是靠运气。

## 复盘问题

1. 原子性违反和顺序违反分别会导致什么问题？
2. 死锁四个必要条件分别是什么？
3. 为什么统一锁顺序能破坏循环等待？
4. 事件循环减少了哪些复杂性，又引入了哪些复杂性？

## 小结

并发 bug 可以分成两大类：继续运行但结果错误，以及无法继续推进。

前者通常和原子性、顺序有关。后者典型形式是死锁。理解这些模式后，再看锁、条件变量、信号量和事件循环，就不会只停留在 API 用法上。
