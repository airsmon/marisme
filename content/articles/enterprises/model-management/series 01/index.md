如果你最近在看 `One API`、`new-api`、`Portkey AI Gateway`、`VoAPI`、`CoAI` 这类项目，十有八九不是因为你突然对“API 转发”产生了文学兴趣，而是因为企业里开始同时出现了这些现实问题：

- 员工已经在用不止一种模型
- 各业务线在各自保存 API Key
- 成本开始上升，但很难复盘
- 平台团队想统一入口，业务团队又不想被卡死

这时候，“模型聚合管理平台”就不再是一个开发者玩具，而是企业把模型接入、权限、路由、计费和审计统一起来的基础设施。

先给结论。

- 如果你只是个人自用或小团队快速上线，`One API` 和 `new-api` 通常更容易起步。
- 如果你要做企业内部统一网关治理，`Portkey AI Gateway` 和 `new-api` 更值得优先看。
- 如果你准备把模型能力做成对外 API 业务，`CoAI` 和 `VoAPI` 会比纯网关型项目更贴近运营场景。

它们并不是同一类产品，只是都被人粗暴地放进了“模型聚合平台”这个筐里。

## 背景与问题

企业第一次接模型服务时，往往只有一个目标：先调通。  
真正麻烦的，通常发生在“调通以后”。

常见演化路径大概是这样：

1. 某个团队先接了 `OpenAI` 或 `DeepSeek`
2. 另一个团队又接了 `Claude`、`Gemini` 或 `Azure OpenAI`
3. 大家开始复制 Key、写代理、做模型名映射
4. 预算、限额、故障切换、审计日志全部散在不同脚本和不同服务里

到这个阶段，企业真正缺的已经不是“再接一个模型”，而是一个统一层。

这个统一层至少要解决五件事：

- 统一接入：下游应用尽量用一套协议接多个模型
- 统一密钥：上游厂商 Key 不在每个业务系统里乱飞
- 统一路由：失败重试、负载均衡、模型切换有地方配置
- 统一管理：哪些人能调哪些模型，能花多少钱，要有边界
- 统一留痕：出了事故以后，知道是谁、什么时候、因为什么请求把事情搞大

## 这类平台到底在解决什么

可以把这类平台理解成企业的“模型接入控制面”，它向上连接员工、内部系统和外部客户，向下连接不同模型供应商，中间负责权限、配额、路由、计费和日志。

按产品重心看，这 5 个项目大致分成三类：

| 类型 | 核心目标 | 典型代表 |
|------|----------|----------|
| 网关型 | 协议兼容、回退、缓存、观测、安全治理 | `Portkey AI Gateway` |
| 管理分发型 | 渠道管理、令牌分发、额度控制、后台管理 | `One API`、`new-api` |
| 运营平台型 | 多租户、订阅充值、品牌前台、对外售卖 | `CoAI`、`VoAPI` |

这就是为什么很多团队一开始以为“它们差不多”，真正上线后才发现，自己拿一个适合对外卖 API 的平台去做内部统一网关，或者拿一个偏 SDK 网关的项目去做客户运营后台，都很别扭。

## 5 个项目的定位差异

先把公开定位摆清楚。

- [CoAI](https://github.com/coaidev/coai) 把自己定位成多租户 AI 一站式方案，强调 200+ 模型、35+ 提供商、内建计费、订阅、文件解析、搜索和聊天能力。
- [VoAPI](https://github.com/VoAPI/VoAPI) 的定位是高颜值、高性能、高扩展的 API 聚合分发系统，公开功能表里明显偏用户体系、规则引擎、计费与运营。
- [new-api](https://github.com/QuantumNous/new-api) 强调统一模型中枢与多协议转换，重点是 OpenAI、Claude、Gemini 之间的兼容转换、权限和计费能力。
- [Portkey AI Gateway](https://github.com/Portkey-AI/gateway) 强调企业级网关、可靠路由、Guardrails、安全和可观测性。
- [One API](https://github.com/songquanpeng/one-api) 则更像最典型的“统一 OpenAI 风格 API 管理与分发系统”，部署轻，入口简单，生态认知度高。

### 总对比表

| 项目 | 定位 | 适合对象 | OpenAI 兼容 / 多协议 | 多租户 / 用户体系 | 计费充值 | 路由与重试 | 权限与组织管理 | UI 完整度 | 企业落地难度 |
|------|------|----------|----------------------|-------------------|----------|-------------|----------------|-----------|--------------|
| `One API` | 统一 API 管理与分发 | 个人、小团队、内部平台起步 | 强 OpenAI 兼容，支持多家模型 | 有用户、分组、令牌体系，但组织治理较轻 | 有额度、兑换码、倍率 | 支持负载均衡、失败重试 | 适合基础管控，不算重治理 | 中等 | 低 |
| `new-api` | 统一模型中枢与兼容层 | 小团队、内部平台、平台团队 | 强，且支持 OpenAI/Claude/Gemini 格式转换 | 权限、分组、OIDC 更完整 | 有组织级计费、缓存统计 | 支持权重随机、自动重试 | 比 One API 更适合企业内部接入 | 中高 | 中 |
| `Portkey AI Gateway` | 企业级 AI 网关 | 平台团队、架构团队 | 强，强调统一 API 与多模态 | 更偏 RBAC、工作区、密钥治理 | 偏成本分析，不是传统运营充值平台 | 强，含回退、负载、超时、缓存 | 强，适合统一治理 | 中 | 中高 |
| `VoAPI` | API 聚合分发与运营平台 | 创业团队、外部服务平台 | 强 | 强，多用户、多等级、多余额 | 强，Pro 明显强化支付与开票 | 强，含重试、熔断、规则 | 中高，但更偏业务运营侧 | 高 | 中高 |
| `CoAI` | 多租户 AI 一站式方案 | 创业团队、产品化团队、对外平台 | 强 | 强，多租户与订阅体系明确 | 强，含订阅和弹性计费 | 强，优先级与权重路由明显 | 中，治理能力够用但重心在产品化 | 高 | 中高 |

这张表最重要的一行，不是“谁功能最多”，而是“适合对象”。

很多选型错误，恰恰发生在这里：

- 想做企业内部统一网关，却挑了一个主要为 C 端或对外运营设计的系统
- 想做对外 API 业务，却挑了一个只把转发做得很强、但没有运营后台的网关

## 关键功能模块对比

这一节更适合直接看表。

| 模块 | `One API` | `new-api` | `Portkey` | `VoAPI` | `CoAI` |
|------|-----------|-----------|-----------|---------|--------|
| 协议与模型兼容 | 标准 OpenAI 风格，易上手 | OpenAI/Claude/Gemini 兼容更强 | 强调统一 API、多模态、Realtime | 兼容广，但重点偏运营分发 | 兼容广，重点偏产品一体化 |
| 路由与重试 | 多渠道、负载、自动重试 | 权重随机、自动重试 | 回退、超时、缓存、条件路由更完整 | 规则引擎、重试、熔断更强 | 优先级、权重路由明显 |
| 用户/组织 | 用户、分组、令牌，基础管控 | 分组、权限、OIDC 更适合企业 | 工作区、角色、密钥治理更强 | 多用户、多等级、多余额 | 多租户、订阅体系明确 |
| 计费与配额 | 额度、倍率、兑换码 | 组织级计费、缓存统计 | 偏成本分析与治理 | 偏充值、支付、运营 | 偏订阅、弹性计费 |
| 观测与审计 | 有明细和渠道管理 | 有统计和账务视角 | observability、安全、guardrails 最强 | 节点监控、行为分析更突出 | 后台与计费视图完整 |
| 前台与后台 | 偏管理平台 | 偏管理平台 | 偏控制台 | 前后台完整、运营感强 | 前后台完整、产品感强 |
| 私有化难度 | 低 | 中 | 中高 | 中高 | 中高 |

读这张表时可以抓一个最实用的判断：

- 你要先统一接口，优先看 `One API`、`new-api`
- 你要做企业治理底座，优先看 `Portkey`
- 你要做对外分发和运营，优先看 `VoAPI`、`CoAI`

## 在企业落地时真正重要的能力

把功能表看完以后，企业真正要问的，不是“它有多少按钮”，而是下面三件事。

### 1. 员工怎么接入

如果平台接进去以后，开发团队还要自己保存上游 Key、自己写适配层、自己记模型映射，那统一平台其实没有真正成立。

更合理的目标是：

- 员工只拿内部统一 Key 或统一网关地址
- 下游系统尽量只认一套调用方式
- 模型切换由平台层处理，而不是每个应用各改一遍

### 2. 成本怎么控

企业怕的不是花钱，而是“不知道为什么花、花在谁身上、能不能提前刹车”。

所以配额、分组、模型访问限制、用量明细、缓存命中统计，都是治理能力，不只是后台小功能。

### 3. 风险怎么管

这里的风险至少包括：

- 上游 Key 泄露
- 某个模型或渠道异常
- 某个业务流量突然暴涨
- 敏感数据被不合适的模型处理

如果平台对这些事情只能“出事以后看日志”，那它更像转发器，不太像企业底座。

## 场景梯队与选择建议

这里不做单一总榜，只做场景梯队。

### 个人 / 快速部署梯队

**第一梯队：`One API`、`new-api`**

原因：

- 部署认知成本低
- 统一 API 入口清晰
- 小团队也能很快看懂系统在干什么

**第二梯队：`CoAI`**

原因：

- 功能完整，但对纯个人用户略重
- 如果你不仅要 API，还要直接面向终端用户提供 UI，会更合适

### 企业内部治理梯队

**第一梯队：`Portkey AI Gateway`、`new-api`**

原因：

- 一个偏企业级治理与可观测
- 一个偏协议兼容、权限和内部计费平衡

**第二梯队：`One API`**

原因：

- 起步很好用
- 但到更复杂组织治理时，通常需要你自己补更多制度和外围能力

### 对外 API 运营梯队

**第一梯队：`CoAI`、`VoAPI`**

原因：

- 多租户、用户体系、计费订阅、前后台完整度更贴近业务平台

**第二梯队：`One API`**

原因：

- 可以做，但更像“能跑起来”，不天然等于“适合长期运营”

### 不适合某些场景的典型原因

- `Portkey` 不适合直接拿来当完整对外运营平台，因为它更像企业网关，不是完整售卖系统
- `CoAI` 和 `VoAPI` 不一定适合最轻量的内部统一入口，因为它们的产品心智更重
- `One API` 不一定适合所有大型组织治理场景，因为它更擅长“统一入口”，不等于自动具备完整企业制度

## 总结

这五个项目都能帮你把“多模型接入”这件事做得比手写脚本更像样，但它们解决的并不是同一道题。

- `One API` 适合先把统一入口搭起来
- `new-api` 适合在统一入口基础上进一步做兼容、权限和内部计费
- `Portkey AI Gateway` 适合把网关层做成真正的企业治理底座
- `CoAI` 和 `VoAPI` 更适合把模型能力做成带用户体系和商业逻辑的平台

如果你现在还在第一阶段，别急着追求“大而全”。  
先回答一个最实际的问题：你要服务的是员工，还是客户。

这个答案，基本就决定了你该先看哪一类项目。
